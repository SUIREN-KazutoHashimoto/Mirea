# サーバーとアプリを更新する

サーバー、Web/PWA、Android APKは更新する場所が異なります。まず「どの版を使っていて、どの版へ進めるか」を確認し、サーバー更新前には復元できるバックアップを用意します。

対象: Mirea `1.0.0`。0.xからの移行では、サーバーを先に更新し、Androidを同じメジャーの版へ更新します。

## 更新するものの違い

| 対象 | 更新する場所 | 更新後の確認 |
| --- | --- | --- |
| サーバー | Docker/TrueNAS等の基盤、または直接起動の設置先 | `/api/health`、ログイン、作品、ジョブ、鍵 |
| Web/PWA | サーバーのWeb配布物 | 起動時の更新反映、表示版、再生。保存データを消して更新しない |
| Android APK | アプリの更新機能、または同じ署名のAPK | アプリ版、接続、再生、保存、更新状態 |
| APK更新情報 | 発行者が署名付きJSONを保守 | 署名・期限・公開APKの対応 |

Androidの更新案内は標準で**接続しているサーバーと同じ公開リリース**を参照します。サーバーが古いままでは、GitHubに新しいAPKがあるだけでその版の案内へ切り替わるわけではありません。

## 1. 更新前に確認する

1. Mireaの設定または `/api/health` でサーバー版を記録します。TrueNASのCustom App表示版だけを使いません。
2. [リリースノート](https://github.com/SUIREN-KazutoHashimoto/Mirea/releases)で対象版の変更・DB移行・制限を読みます。
3. 実行中のイメージタグとdigest、起動設定、マウント先、UID/GIDを記録します。
4. 転送とジョブが終わる時間を選びます。
5. [完全バックアップ](backup-restore.md)を取得します。分離したdata/media、設定、証明書は同じ停止時点の組で保管します。

## 2. Dockerの固定タグを更新する

以下は単一保存先の例です。追加のComposeファイルを使う環境は、すべてのコマンドに同じ `-f` を追加します。プロジェクト名も変えません。

1. サーバーを停止します。

   ```sh
   docker compose -p mirea -f compose.release.yaml stop mirea
   ```

2. 停止状態のバックアップを確認します。
3. `compose.release.yaml` の `image` を対象リリースのタグまたはdigestへ変更します。他の保存先設定は維持します。
4. 次を順に実行します。

   ```sh
   docker compose -p mirea -f compose.release.yaml config --quiet
   docker compose -p mirea -f compose.release.yaml pull
   docker compose -p mirea -f compose.release.yaml up -d --wait
   docker compose -p mirea -f compose.release.yaml ps
   ```

5. HTTPSの `/api/health` と実際のログイン・作品の閲覧を確認します。

`beta` / `stable` の追従タグは、同じタグ名に新しい公開済みイメージが割り当てられます。**タグを設定しただけで稼働中コンテナが自動更新されるわけではありません**。取得と再作成が必要です。[チャネルの詳細](../container-channels.md)

## 3. TrueNASなどの管理画面を使う

1. Appを停止し、Host Pathの両データセットと設定を保管します。
2. 固定タグなら編集画面で対象タグへ変更します。追従タグなら基盤のイメージ更新確認・再取得操作を使います。
3. 同じ保存先・実行ID・証明書で起動します。
4. Mirea本体の版と、作品の閲覧・保存を確認します。

更新ボタンが出ないときは、固定タグのままか、イメージ検査が済んだか、Pull Policyがキャッシュ優先かを確認します。ボタンを出すためにアプリやデータセットを削除しません。MireaからDockerソケットやNAS管理APIへ接続して更新する機能はありません。

## 4. Node.js直接起動を更新する

1. 新版コードを旧版とは別のフォルダーへ展開します。
2. 対応するNode.jsで依存関係を導入します。完成品の `server.tar.gz` は `pnpm install --prod --frozen-lockfile` だけを実行します。ソースZIP／cloneは `pnpm install --frozen-lockfile`、`pnpm build` の順に実行します。まだデータを起動しない準備段階です。[配布物の選び方](../install/native.md)
3. 旧サービスを停止して、data/mediaと設定の完全バックアップを取ります。
4. 新版の `.env` に同じデータ領域とTLS設定を引き継ぎます。変更された設定の意味はリリースノートと照合します。
5. サービスが起動するコードのパスを新版へ切り替え、一般ユーザーのまま起動します。
6. 版・ログイン・閲覧・ジョブを確認します。旧コードとバックアップは復旧確認まで残します。

環境限定の更新ヘルパーは、任意のWindowsホストへそのまま導入できる汎用機能ではありません。未導入環境はこの手動更新を使います。

## 5. Androidアプリを更新する

1. サーバーへ接続し、アプリの更新画面で確認します。
2. 更新が提示されたらダウンロード・適用へ進みます。
3. Androidが提供元の許可やインストール確認を求めた場合は、画面の内容を確認して操作します。
4. 更新後、同じサーバーへ接続して版を確認します。

自動確認・条件を満たす回線での取得・自動適用は維持しています。Android/端末の条件によって最終確認が必要で、常に無操作で更新できるわけではありません。更新時にアプリをアンインストールする必要は通常ありません。アンインストールは端末内データを失います。

更新JSONの有効期限は最大7日で、APK署名とは別です。期限切れ・配信失敗では検証を省略せず更新を止めます。発行者側の保守が必要です。[Android更新設計](../android-updates.md)

## ベータ版から正式版へ移るとき

1.0.0への移行は、[GitHub Release](https://github.com/SUIREN-KazutoHashimoto/Mirea/releases/tag/v1.0.0)が公開され、対応APKとイメージを取得できることを確認してから行います。ドラフトやソースブランチ上の版番号だけでは、配布完了を意味しません。

`beta` と `stable` は別の追従先です。正式版を公開しても `beta` を正式版へ自動で付け替えることはありません。ベータ版利用者が1.0.0へ移るには、サーバーの固定タグを `1.0.0` にするか、正式版用の `stable` へ明示的に切り替えます。切替後も取得とコンテナの再作成が必要です。

メジャー番号が変わる場合は、次の順序で進めます。

1. 同じ配布元・APK署名の正式版が公開されていることを確認し、完全バックアップを取ります。
2. サーバーを対象正式版へ更新し、Webで起動とデータを確認します。
3. Androidアプリで同じサーバーへ接続し、更新案内から正式版へ更新します。メジャー不一致時も更新確認のための通信は利用できます。作品の利用は互換性のあるアプリへ更新してから再開します。
4. APKの上書き更新後に、保存済み作品・続き位置・通常再生を確認します。アプリの削除や保存領域の初期化はしません。

更新情報の定期再署名は、公開中の最も新しいメジャーバージョンを対象とします。新しいメジャーの公開後、旧メジャーの既存JSONは残りの有効期間が過ぎると更新案内に使えなくなります。旧APK・Release・鍵を削除するという意味ではありません。発行者は新メジャーのリリースノートに保守終了日と移行先を明記します。サーバーを旧版のまま運用し続ける場合、そのサーバーが提示する旧APK更新案内も継続保守されない点に注意してください。

**メジャー0の定期再署名は、1.0.0の公開日時をもって終了します。** 既存のRelease・APK・更新JSON・鍵は残します。旧版の更新案内が期限切れでも、先にサーバーを1.0.0へ更新すれば、そのサーバーから1.0.0の更新を確認できます。必要なら公開Releaseの同一署名APKを手動で上書きインストールしてください。期限検証や署名検証を無効にする必要はありません。

## 不調時の切り戻し

新しいDBを古いサーバーコードで開くことは、安全な切り戻しではありません。

1. 不調な新版を停止し、追加調査用に現在の状態を保管します。
2. 更新前のコード／イメージと、**それに対応する更新前の完全データ・設定**を別の保存先へ復元します。
3. 復元した側だけを起動して確認します。
4. 更新後に追加した作品や記録は、更新前バックアップには含まれません。上書きで失う前に扱いを決めます。

DB、ダウンロード鍵、ストレージ識別ファイルを削除して起動検査を通そうとしないでください。復元不能な場合は停止状態を保ち、[安全な診断情報](troubleshooting.md)を使って調べます。
