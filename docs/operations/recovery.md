# 自動保全と障害からの復旧

Mireaの自動保全は、DB・暗号鍵・設定・保存先の識別情報を対象にします。作品本体・表紙・プレビュー・AIモデルはコピーせず、ホスト側のスナップショットやバックアップで保管します。Mireaを唯一の管理先にする前に、**メタデータと対応する作品を組み合わせ、別の空の保存先へ戻す試験**まで行ってください。

2.1.1beta以降、自動・更新前の保全はメタデータのみです。2.1.0betaの全体コピー方式とは対象が異なるため、メディア本体のホスト側バックアップを併用してください。

## 初期状態で行うこと

| 保全 | 間隔・タイミング | 内容 |
| --- | --- | --- |
| DB・鍵 | 5分。スケジュールの確認は1分ごと | 整合したSQLiteスナップショット、keys、保存先識別、設定 |
| 更新前 | サーバー版またはスキーマが変わる起動時 | DBを変更する前のメタデータ復旧点。作れなければDB変更を始めない |
| 検査 | 起動、保全、復旧点の明示的な検証 | DBの構造・外部キー、保管ファイルのSHA-256 |

DB保全はSQLiteのオンラインバックアップAPIを使い、通常操作を止めません。メディア本体の容量や実行中ジョブ数に応じた全体コピーを待つ必要はありません。ホスト側の完全バックアップと、更新前の停止中スナップショットは、別途[更新手順](updates.md)に従って用意します。

同じ内容のファイルは復旧点間で共有します。稼働中ファイルへのハードリンクは作らず、独立したコピーまたはコピーオンライト複製を保存します。

## 管理画面で確認する

1. 「サーバー管理 → 自動保全・復旧」を開きます。
2. メタデータの最終保全日時と、失敗表示がないことを確認します。
3. 「保存間隔と保持期間」で設定します。管理者パスワードが必要で、変更は次の保全から反映します。環境変数の上書きがある項目には指定値が表示されます。
4. 「メタデータを今すぐ保全」を実行して最初の復旧点を作成します。
5. 復旧点の「検証」を実行し、検証日時が表示されることを確認します。

初期の保持期間は30日です。直近24時間を細かく、7日までは1時間ごと、それ以前は1日ごとに残し、最新2件を必ず残します。**手動と更新前の復旧点は自動削除しません。** 不正な保全情報がある場合は整理を中止します。失敗時に古い正常な復旧点を消して空きを作ることはしません。旧版が作成した全体復旧点も、その検証・復元互換性を保ちます。

## 保存先と別媒体への複製

標準は `DATA_DIR/recovery` で、追加設定なしで有効です。DB・鍵だけの復旧点で作品本体を保護したことにはなりません。

自動保全は平文の機密データを含みます。公開Web領域や共有フォルダーへ置かず、外部保管には暗号化されたストレージ／バックアップ製品、または[手動の暗号化バックアップ](backup-restore.md)を使ってください。

別の保存先は起動設定の `RECOVERY_DIR` で指定します。**既に存在する、実行ユーザーが読み書きできるフォルダー**が必要です。data/mediaと独立した場所、または標準のdata/recoveryを指定します。未接続のマウントをコンテナ内の空フォルダーで代用しません。別のライブラリの保全先を使い回せません。

コンテナではホスト側の専用バックアップ領域を、固定の `/recovery` へ読み書きマウントし、`RECOVERY_DIR=/recovery` とします。ディレクトリーの所有者をサービスUID、モードを0700にします。明示した永続マウントを確認できなければ起動を拒否し、コンテナの空フォルダーやtmpfs等へ保存を続けません。特権やDockerソケットは不要です。保存先変更前に旧保全先も丸ごと保管します。

必要容量はDB・鍵・設定の世代数に依存し、メディア全体と同じ容量を事前確保する必要はありません。DBの内容が変わるたびに独立したDBを保存するため、DBが大きい環境では世代数も含めて見積もります。既定では512MiBの空きを残します。保持期間は容量の保証ではなく、保護する更新前・手動の復旧点でも容量が増えます。

別データセットならdata用のクォータと保全用のクォータを分けられます。ただし、同じプール内の別データセットだけではプール全体の故障には備えられません。

別媒体へは `recovery-store.json`、`snapshots`、`objects` を含む**保全フォルダー全体**を複製します。最も簡単なのはMireaを停止してから複製する方法です。ホスト側のスナップショット・世代付きバックアップ・別装置への複製を併用します。同じディスク内のコピーだけではディスク故障に備えられません。

## オフラインで検証する

Node.js 24と対象のMirea配布物を用意します。以下は**配布物のルート**で実行します。パスとIDは、自分のバックアップと画面に表示された復旧点IDへ置き換えてください。利用中サーバーや稼働中DBへの操作は行いません。

Linux / macOS:

```sh
node scripts/recover-data.mjs --store=/backup/mirea/recovery --snapshot=11111111-1111-4111-8111-111111111111 --verify-only
```

Windows PowerShell:

```powershell
node scripts/recover-data.mjs --store=C:/MireaBackup/recovery --snapshot=11111111-1111-4111-8111-111111111111 --verify-only
```

`verified: true` が成功です。欠落・チェックサム不一致・DB不整合があれば失敗します。元データへ自動復元したり、正常な復旧点を壊れたものへ上書きしたりしません。

## メタデータを取り出して復旧する

通常の復元コマンドは、作品本体を含まない復旧点を全体復元と誤認しないよう拒否します。停止中の管理作業として `--metadata-only` を明示し、別の空の作業先へ取り出します。

```sh
node scripts/recover-data.mjs --store=/backup/mirea/recovery --snapshot=11111111-1111-4111-8111-111111111111 --destination=/restore/metadata --metadata-only
```

`verified: true`、`restored: true` と `restore-result.json` を確認します。DB・鍵・保存先識別情報等は取り出せますが、作品本体・表紙・プレビュー・AIモデルは戻りません。ホスト側のバックアップから別の保存先へ復元した対応データと組み合わせ、DBが参照するファイル・配信世代が存在することを確認してください。稼働中の保存先へDBだけを上書きしません。

アカウント・本棚・シリーズ・履歴・続き位置・AI解析情報等はDBに含まれます。カスタム表紙の原本やモデルの重みはファイル側なので、ホスト側の保管が必要です。更新前へ完全に切り戻す場合は、同じ停止時点のdata/mediaと設定・旧コードを基本とします。

## 旧版が作成した全体の復旧点から戻す

以下は2.1.0beta等がすでに作成した `scope=full` の復旧点用です。メタデータ限定の保全サービスが新しい全体コピーを作る操作ではありません。

1. Mireaを停止します。障害が起きたdata/mediaは削除せず保存します。旧新2プロセスから同じ保存領域を開かないでください。
2. 元データと保全フォルダーの**どちらとも別の、空の復元先**を用意します。
3. 配布物のルートで次を実行します。Windowsでは `--destination=C:/MireaRestore` 等を使います。

   ```sh
   node scripts/recover-data.mjs --store=/backup/mirea/recovery --snapshot=11111111-1111-4111-8111-111111111111 --destination=/restore/mirea
   ```

4. `verified: true`、`restored: true` と復元先の `restore-result.json` を確認します。途中失敗は完了扱いにならず、未完了マーカーがある保存先ではMireaを起動できません。別の空フォルダーで再試行します。
5. 復元先の `data` をDATA_DIRにします。分離構成は同じ復元先の `media` をMEDIA_DIRにします。結合構成はMEDIA_DIR未設定を維持します。保存先の識別情報も復元されます。
6. 切り戻しには**更新前の版と、その時点の設定**を使います。初回移行で更新前の版が「未記録」なら保管した旧タグ／digestを確認します。新しいDBへ旧コードだけを戻しません。
7. `configuration` は保管資料で、サービスへ自動適用されません。絶対パス・公開範囲・証明書パス・実行UID/GIDを確認します。外部プロキシ・CA管理情報・コンテナ定義・イメージdigestは別途保管が必要です。
8. 復元先だけを起動し、アカウント、本棚、シリーズ、本・動画・音声、続き位置、保存済み作品の再認証を確認します。

復元にはOS標準tarが必要です。PAX形式でナノ秒のファイル時刻を保持し、既存の暗号化ダウンロードが参照する識別情報を維持します。復元先の時刻精度が低い場合は、端末での再取得が必要になる場合があります。

### DB・鍵だけの復旧点

現在の自動保全はメタデータが対象です。対応するメディアはホスト側で別途保管します。通常の復元コマンドはメディアを含まない復旧点を拒否します。

`--metadata-only` を明示すると空の作業先へDB・鍵等を取り出せますが、作品本体は戻りません。停止中の保存領域の複製と組み合わせ、参照する作品・配信世代が存在することを確認する管理作業が必要です。DBだけの切り替えを完全なロールバックとは扱いません。

## 目標と限界

- DBの損失を通常5分程度に抑えることを目指しますが、停止・容量・処理状況で遅れるため保証値ではありません。画面の成功時刻を確認します。
- 作品本体の損失範囲は、ホスト側のバックアップ間隔で決まります。メタデータ保全だけでは、失った作品ファイルは戻りません。
- 復旧時間は容量と保存先次第です。空の環境へ戻す試験で実測します。
- 既に壊れていた作品を推測して直す機能ではありません。元ファイルを削除する前に、取り込み結果と復元した作品を実際に開いて確認します。
- アプリが書ける保全先だけでは、誤操作・侵害・装置故障すべてには備えられません。ホスト側で管理する変更不可のスナップショットと別媒体を併用します。
