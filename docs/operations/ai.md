# ローカルAIを準備する

Mirea 2.0.0beta向けの手順です。1.0.0以前にはこの画面はありません。[対象版と検証範囲](../status.md)も確認してください。

推論は導入先のCPUで動き、対応環境ではVulkanも選べます。外部の推論APIは使いません。管理者がモデルを選び、本棚所有者が解析を有効にすると、利用者がタグ・本文・曲の構成・動画の章を使えます。

## 1. 必要なもの

| 項目 | 目安・確認すること |
| --- | --- |
| RAM | 16GiB以上を推奨。4B視覚モデルは重み約5GiBと実行用メモリーを使う。少ない環境では2Bを選ぶ |
| CPU | 最初は4スレッド・同時解析1。閲覧や転送への影響を見て調整する |
| 保存容量 | モデル、解析情報、一時処理分を確保する。取得前にモデルの正確な容量を表示する |
| GPU | 必須ではない。Vulkan対応GPU、ドライバー、実行エンジンがそろう場合だけ選ぶ |
| バックアップ | 初回更新前にデータと設定を完全バックアップする。[手順](backup-restore.md) |

曲の構成解析は、曲全体の音源分離と8モデルの合議をCPUで行います。長い曲ほど時間とメモリーを使います。予算に収まらない処理は準備待ちに置かれます。短い試聴部分だけを曲全体の解析結果として保存する処理はしません。

## 2. 実行エンジンを導入する

AI対応コンテナには実行コードだけが含まれます。この節の追加導入は、直接Node.jsで起動する場合です。モデルの重みはコンテナにも含まれません。

サーバーを停止し、Mireaの `package.json` があるフォルダーで実行します。コードの配置先はサービス用利用者から書き換えられないようにし、利用者データの中へ実行ファイルを置きません。

Windows x64は、公式の固定版バイナリーをSHA-256で確認して導入します。Webサービスを管理者として起動する必要はありません。

```powershell
node scripts/install-ai-engines.mjs --backend=both --accept-runtime-licenses
```

CPUだけなら `--backend=cpu` にします。Windows公式バイナリーのCPU命令要件も配布元で確認してください。LinuxはGit、CMake、C/C++コンパイラーを先に用意します。Debian系の例です。

```sh
sudo apt-get update
sudo apt-get install build-essential cmake git libvulkan-dev glslc spirv-headers
node scripts/install-ai-engines.mjs --backend=both --accept-runtime-licenses
```

モデルを取得せず、`ai/runtime-versions.json` の固定コミットからビルドします。Linuxの推論用通信制限ランチャーも作成します。LinuxでVulkanを選ぶと、Khronos公式の固定版Vulkan-Headers（vulkan-sdk-1.4.363.0）をビルド作業領域へ取得し、OS付属ヘッダーの古さによるコンパイル不整合を避けます。実行時のVulkanローダーとドライバーはOS側のものを使い、ヘッダーの利用条件と取得元も導入先へ保存します。異なる既存実行コードは勝手に上書きしません。Vulkanを使わないなら `--backend=cpu` でGPU用ビルドを省略できます。

### 曲の構成解析も使う場合

Python 3.11または3.12を用意します。LinuxではPythonのvenvとlibsndfileも必要です。Mireaのフォルダーで実行します。

```sh
node scripts/install-ai-music.mjs --accept-runtime-licenses
```

CPU用PyTorchと音楽解析コードを専用venvへ入れます。モデルは取得しません。Pythonの場所を選ぶ場合は `--python=<実行ファイルのパス>` を指定します。依存コードの利用条件・表示文書は、導入先の `ai/bin/notices` に保存されます。

## 3. 管理画面でモデルを取得する

1. 管理者でログインし、「サーバー管理」→「AI機能」→「モデル」を開きます。
2. 「利用条件を確認して取得」を選びます。
3. 公式配布元の固定版、ライセンス、容量を確認します。条件確認のチェックと現在の管理者パスワードを入力します。
4. 「使用可能」になるまで待ちます。中断・再開でき、画面を閉じてもサーバー側で続きます。
5. 「設定」に戻り、機能別に導入済みモデルを選びます。

| 機能 | モデル |
| --- | --- |
| タグ、OCR、動画の章 | Qwen3-VL 4B（品質優先）または2B（省メモリー） |
| 文字起こし | Whisper large-v3（品質優先）またはsmall |
| 曲の構成 | All-In-One harmonix ensemble **とHTDemucs前処理モデルの両方** |
| 意味検索の索引 | Qwen3 Embedding 0.6B |

重みは `DATA_DIR/ai/models/<モデルID>` に保存します。取得元、固定版、ファイル名、容量、SHA-256、利用条件の確認記録を保持します。使用中や索引が参照中のモデルは削除できません。管理者の操作なしで新版モデルへ切り替えません。

## 4. 設定して動作確認する

最初はCPU、4スレッド、同時解析1を選びます。モデル用予算はOSや通常再生の分を残して設定します。「解析の詳細設定」では文脈、出力、起動待ち、解放時間を変えられます。解析時間帯も限定できます。

設定保存後に「合成データで動作確認」を実行します。利用者のアセットを使わず、モデル起動、合成画像の認識、同じ合成文の索引生成などを試します。各作品の認識精度を保証する評価ではありません。

「AIによる解析」を有効にして保存します。これだけで既存全作品を一斉解析することはありません。本棚所有者が本棚メニューの「本棚の解析」で新しい作品の自動解析を有効にします。既存分は別の操作で依頼します。

## Vulkanを使う場合

直接起動ではVulkan版エンジンと対応ドライバーを導入し、管理画面でVulkanを選びます。起動できないときはCPUへ戻します。曲の構成解析はCPUを使います。

LinuxコンテナではOS管理者がDRM renderデバイスを1つだけ割り当てます。以下は追加設定の例です。デバイスとアクセス用グループ番号は自分のホストで確認してください。例の `RENDER_GROUP_GID` は、対象デバイスへの既存のアクセス権を持つグループの数値GIDへ置き換えます。

```yaml
services:
  mirea:
    devices:
      - /dev/dri/renderD128:/dev/dri/renderD128
    group_add:
      - "RENDER_GROUP_GID"
    environment:
      AI_VULKAN_RENDER_NODE: /dev/dri/renderD128
```

既存のデバイスアクセス権が必要です。特権モード、capability追加、デバイス全体の割り当てで回避しません。保護機構は指定したroot所有のrenderデバイスだけに書き込みを許可します。ソフトウェアVulkanはGPU検出成功として扱いません。

CPU専用の開発環境ではGPUの実動作・機種差を検証できません。導入先で短い動作確認を行い、通常再生への影響を見て対象を増やしてください。

## 接続できないサーバーへ導入する

外部へ接続できる別PCのMireaフォルダーで、一覧と利用条件を確認します。保存先はソースの外にします。

```sh
node scripts/download-ai-model.mjs --list
node scripts/download-ai-model.mjs --key=vision-4b --destination=/srv/mirea-model-import
```

表示された条件と固定版を確認してから、保存されたJSONで取得します。

```sh
node scripts/download-ai-model.mjs --manifest=/srv/mirea-model-import/mirea-model-vision-4b.json --destination=/srv/mirea-model-import --accept-model-terms
```

Windowsでは `--destination=C:/MireaModelImport` のように読み替えます。JSONと、表示されたモデルIDフォルダー内のファイルをサーバーへ手動転送します。モデルを再配布する場合の条件は別途確認してください。

サーバー側のMireaフォルダーで、正しいサービス用所有者として実行します。パスは自分の配置へ置き換えます。

```sh
node scripts/import-ai-model.mjs --manifest=/srv/import/mirea-model-vision-4b.json --source=/srv/import/model-files --data-dir=/srv/mirea/data --accept-model-terms
```

既存DBを開かず、容量・SHA-256を確認して配置します。異なる既存ファイルは上書きしません。最後に管理画面の「接続できないサーバーへモデルを導入」で同じJSONを選び、利用条件を確認して登録します。この登録は配置済みファイルだけを検証し、外部から取得しません。

## 困ったとき

| 状態 | 対応 |
| --- | --- |
| 実行エンジン未導入 | コードの導入先と実行条件を確認。モデル取得だけでは動かない |
| 準備待ち | モデル、音楽の前処理、メモリー、一時保存容量を確認 |
| 一部未解析 | 解析の状況から未解析分を再試行。成功したページは保持する |
| モデル取得失敗 | HTTPS接続、容量、配布元の条件を確認して同じ固定版を再開 |
| 古い版のアプリ | 同じメジャーの対応アプリを使う。保存領域を初期化して回避しない |

重み、入力、生成文は通常ログへ出力しません。障害報告には安全なコードと動作確認の結果を使います。[利用者の操作](../user/ai.md)へ進んでください。

## ライセンス文書とバックアップ

「Mireaについて」から「AI実行ライブラリーのライセンス」を開くと、導入済みの実行コードの表示文書を確認できます。別途取得するモデルの条件は、管理画面のモデル導入記録で確認します。モデルを別途取得しても、その利用条件がなくなるわけではありません。

完全バックアップは解析情報・手動訂正とモデルを含みます。一時作業領域は含みません。メタデータのみのバックアップから復元した場合は、同じ固定版のモデルも復元または再導入してください。
