# バックアップを取得し復元する

作品だけをコピーしても、アカウント・本棚・続き位置・端末保存の鍵は戻りません。DB、保存領域、設定、必要な鍵を同じ時点の組として保管します。

対象: Mirea `2.0.0beta`。復元は停止中の空の保存先で行います。稼働中データへ自動で上書きする復元APIはありません。

## どの方法を選ぶか

| 方法 | 向いている用途 | 保存するもの |
| --- | --- | --- |
| 管理画面の「全体」バックアップ | ブラウザーから取得、別環境へ復元 | DB・鍵・本体・原本・派生データを暗号化したアーカイブ |
| 停止中のファイル／データセットのバックアップ | 更新前の完全退避、同じ構成へ復帰 | data/media全体、隠し識別ファイル、設定、外部の証明書等 |
| 管理画面の「メタデータ」 | DB・鍵の補助的な保管 | 作品本体を含まない。これだけで作品は復元できない |

バックアップは保存サーバーとは別の障害単位にも保管します。同じディスク内のコピーやスナップショットだけでは、そのディスクの故障に備えられません。

## 方法A 管理画面から全体バックアップを取得する

1. 転送とメディア処理が落ち着く時間を選びます。作成中はAPI操作が一時制限されます。
2. 「サーバー管理 → バックアップ」を開きます。
3. 全体モードを選び、機密情報を含むことを確認します。
4. 管理者の現在のパスワードと、**バックアップ用の別の12文字以上のパスワード**を入力します。
5. 完了になるまで待ち、ファイルをダウンロードします。
6. ファイルとパスワードを別々に安全に保管します。サーバー側の生成ファイルは24時間で期限切れになります。

バックアップ用パスワードを忘れると復号できません。パスワードはサーバーへ保存されず、再起動で中断したバックアップは作り直しになります。

開始済みの原本整理や表示用ページの生成・保存が終わるまで待ってから、バックアップを開始します。作成中は新たな原本整理を一時停止し、ファイル一覧の取得後に原本が消えることを防ぎます。メディア変換などが続いている場合は、終了後に再試行してください。

### 含まれる範囲

全体モードはSQLiteの整合したスナップショット、`keys`、`uploads`、`videos`、`originals`、`previews`、`thumbnails`を含みます。分離構成でも論理的な `data/` の下へ集約されます。カスタム表紙の原本、旧配信世代、転送途中データも該当する領域に含まれます。

アプリ設置場所の `.env` があれば同梱します。ただし**コンテナへ外から渡した環境変数、Compose YAML、サービス設定、プロキシ設定がすべて自動保存されるわけではありません**。次も別に保管します。

- 使用した版・コンテナのタグとdigest、Compose/YAML、起動方法。
- 外部に置いたTLS証明書・秘密鍵、CAの管理情報。
- APK署名鍵・更新情報署名鍵を自分で持つ発行者は、その鍵と復旧手順。
- OSのユーザーID・権限・マウント設定と、data/mediaの対応関係。

バックアップ自体はDATA_DIR側に作ります。全体容量に加え、作業用DBと余裕を確保してください。容量不足で失敗した場合は元データを残し、保存容量を確保してやり直します。

## 方法B 停止中に保存先を丸ごと保管する

1. 利用者へ停止時間を案内し、転送・実行中ジョブの完了を待ちます。
2. Mireaを停止します。Docker例:

   ```sh
   docker compose -p mirea -f compose.release.yaml stop mirea
   ```

3. DATA_DIR全体を保管します。分離構成はMEDIA_DIR全体も、同じ停止期間中に保管します。隠しファイル・鍵・所有者・権限・時刻を含めます。
4. 同時点の設定と証明書を別途保管します。バックアップに版番号と取得日時を付けます。
5. バックアップ先から読めることと、容量・ファイル数・必要な鍵が揃うことを確認します。
6. 元の構成を変更しない場合はMireaを再開します。

TrueNAS等のデータセットでは停止中に両方をスナップショットし、別媒体へ複製します。片方だけ別時点のスナップショットへ戻しません。

Dockerのnamed volumeはコンテナのイメージ保存に含まれません。ボリュームのバックアップ方法は[Docker公式手順](https://docs.docker.com/engine/storage/volumes/#back-up-restore-or-migrate-data-volumes)を使用します。実ボリューム名はプロジェクト名によって変わるため、`docker volume ls`で確認します。`down -v`やボリューム削除はバックアップ操作ではありません。

## 暗号化アーカイブを復号する

以降は**Mireaの管理画面で作ったバックアップ**を扱います。OSのスナップショットは、その基盤の復元手順を使います。

Node.js 24と該当版のソースを用意し、**ソースのルート（`scripts`があるフォルダー）**で実行します。入力と出力は、十分な空きのある保護された作業フォルダーを絶対パスで指定します。パスは例です。PowerShellでも同じ `node` コマンドを使えます。

```sh
node scripts/decrypt-backup.mjs --input=/secure/mirea-full.mireabackup --output=/secure/restore.tar.gz
```

Windowsの例:

```powershell
node scripts/decrypt-backup.mjs --input=C:/MireaBackup/mirea-full.mireabackup --output=C:/MireaBackup/restore.tar.gz
```

端末にパスワード入力が出ます。パスワードをコマンド引数へ書きません。認証成功のメッセージが出れば復号完了です。分割ファイルの場合は全パートを `--input=` で列挙します。ファイル名で並べられるため、番号付きの名前を変えないでください。

```sh
node scripts/decrypt-backup.mjs --input=/secure/backup.part-000001 --input=/secure/backup.part-000002 --output=/secure/restore.tar.gz
```

復号後のアーカイブは平文の機密データです。共有フォルダー・クラウド同期・Gitへ置かないでください。

## 空の場所へ展開して確認する

1. `restore.tar.gz`を保存したフォルダーへターミナルで移動します。既存データと別の空フォルダー `restore-work` を作成します。PowerShellでは `New-Item -ItemType Directory -Path ./restore-work`、Linuxでは `mkdir ./restore-work` を使います。既に存在する場合は中身を確認し、別の空の作業先を選びます。
2. 内容を一覧し、パスと `backup-manifest.json` があることを確認します。

   ```sh
   tar -tzf restore.tar.gz
   tar -xzf restore.tar.gz -C restore-work
   ```

3. `restore-work/backup-manifest.json` を開き、`mode`、`schema`、`mediaIncluded`、ファイル一覧を確認します。
4. `restore-work/data/mirea.sqlite` と `restore-work/data/keys` があることを確認します。全体モードならメディアの各フォルダーもあります。
5. Node.jsでDBを読み取り専用検査できます。以下は `restore-work` 内で実行します。

   ```sh
   node --input-type=module -e 'import {DatabaseSync} from "node:sqlite"; const db=new DatabaseSync("data/mirea.sqlite",{readOnly:true}); console.log(db.prepare("PRAGMA integrity_check").all()); console.log(db.prepare("PRAGMA foreign_key_check").all()); db.close();'
   ```

`integrity_check`は `ok`、`foreign_key_check`は空配列が正常です。検査失敗、欠けたパート、パスワード不一致があれば、元データへ上書きせず原因を調べます。

新しいバックアップはPAX形式の拡張でファイルの更新時刻をナノ秒単位まで記録します。Windows標準のtarやGNU tarで展開し、その後のコピーでも更新時刻を保持してください。時刻を含むファイルの識別情報は、既存の暗号化ダウンロードを引き続き使うために必要です。

旧版が作ったアーカイブは、tar内の更新時刻を秒単位で保存しています。原本と暗号鍵が同じでも、復元後に既存のダウンロードが「原本が変更されました」となり、端末での再取得が必要になる場合があります。新しい復号ツールを使うだけで、旧アーカイブの時刻精度が復元されるわけではありません。既存の登録や鍵を削除したり、ファイル検証を無効化したりして回避しないでください。

## サーバーへ復元する

1. 復元先のMireaを停止します。元の保存領域はそのまま残します。
2. **空のDATA_DIR**へ、展開した `data/` の中身を更新時刻を保持してコピーします。`data/data/` という二重階層にしません。コピー元と復元先のファイルシステムで時刻精度が異なる場合は、保存済みデータの再取得が必要になることがあります。
3. バックアップと互換のMireaコードを用意します。古いコードへ新しいDBを渡すダウングレードは行いません。
4. 設定内の絶対パス・証明書パスを復元先へ合わせます。プロセスの実行ユーザーに必要な所有権・権限を設定します。
5. 分離したい場合は、まだ起動せず[保存先の分離手順](../storage.md)でメディアを移してから `MEDIA_DIR` を有効にします。管理画面バックアップは集約形式で、元の分離識別ファイルをそのまま含む方式ではありません。
6. 復元先だけを起動します。同じ保存領域を旧新2プロセスで開かないでください。
7. アカウント、本棚、代表的な本・動画・音声、続き位置、保存済みデータの期限更新を確認します。

Mireaの旧固定パスHTTPS事前検査を有効にした構成は、導入ID・証明書pin・識別ファイルの復元も必要です。空のデータセットへ新規作成する手順を、復元されたDBへそのまま適用しません。[互換検査の条件](../container-security.md#truenas-https事前検査)

ファイルの時刻やURLを変えた場合、端末側が再取得を求めることがあります。端末の保存データをサーバーバックアップの代用にはできません。

## 定期的に確認すること

- 最新のバックアップを実際に復号・検査できるか。
- パスワード・外部証明書・設定をサーバー故障後にも取り出せるか。
- 保存容量、保存世代数、別媒体への複製が続いているか。
- 別の空環境へ復元し、作品を開くまでの手順と時間を確認したか。
