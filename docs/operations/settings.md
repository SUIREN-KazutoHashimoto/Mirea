# 管理者の設定と設定値の優先順位

容量上限・登録可否・処理数は、まずMireaの「サーバー管理」で変更します。保存先、接続ポート、TLS証明書など設置場所に関する値は、OSやコンテナの設定で管理します。

対象: Mirea `2.0.0beta`。設定の名称・範囲は[実装](../../server/operational-settings.js)と[処理設定](../../server/processing-settings.js)に対応します。

## 設定が反映される順番

通常の運用設定は、優先度が高い順に次の値を使います。

1. **サーバープロセスに渡された環境変数。** 管理画面には変数名と適用値が表示され、その項目は変更できません。
2. **管理画面から保存したDB内の設定。** 環境変数の指定がない場合に使います。
3. **プログラムの既定値。** 初期状態ではこの値で動きます。

Node.js直接起動では、OS側の環境変数が `.env` より優先します。Composeでは、ホストの `.env` はYAMLの変数展開に使われます。コンテナへ何が渡るかはYAMLの `environment` を確認してください。

配布済みComposeが `${MAX_UPLOAD_BYTES:-2147483648}` を渡している場合、ホストで値を未指定にしても2 GiBの上書きが続きます。UIへ管理を戻すには、その環境変数の行をYAMLから省き、コンテナを再作成します。既存データのマウントは維持します。

## サーバーの設定

「サーバー管理 → サーバーの設定」で変更します。管理者の現在のパスワードを入力して保存し、**サーバーを再起動すると適用**されます。

| UI項目 | 既定値 | 許可範囲 | 上書きする環境変数 |
| --- | --- | --- | --- |
| アセットの容量上限 | 2 GiB | 1 MiB〜1 TiB | `MAX_UPLOAD_BYTES`（バイト） |
| 分割転送のサイズ | 8 MiB | 64 KiB〜16 MiB | `UPLOAD_CHUNK_BYTES`（バイト） |
| 新規アカウント登録を許可 | ON | true / false | `ALLOW_REGISTRATION` |
| 閲覧記録を収集 | ON | true / false | `ANALYTICS_ENABLED` |

容量を10 GiBにしたい場合はUIへ `10` を入力します。環境変数で固定する場合は `MAX_UPLOAD_BYTES=10737418240` です。「合計容量上限」と「1要求の分割サイズ」は別なので、大きな作品を許可するために分割サイズを10 GiBへ変える必要はありません。

画像書籍には画像1枚100 MiB・1冊1000枚という別の制限があります。合計上限を上げてもこの制限は変わりません。画素数の上限はありませんが、展開後のメモリー消費・処理時間・空き容量は必要です。

閲覧記録の収集をOFFにしても、過去の記録を削除する操作にはなりません。再開位置などの機能は分析用の生ログと別に扱われます。

## 処理の設定

「サーバー管理 → 処理の設定」で変更します。通常、保存後の待機列の実行に反映されます。既に走っている処理を途中で停止したり、強制的に少ない数へ減らしたりはしません。

| 項目 | 既定値 | 範囲 | 環境変数 |
| --- | --- | --- | --- |
| 同時アップロード | 3 | 1〜32 | `MAX_CONCURRENT_UPLOADS` |
| 同時変換・メディアジョブ | 5 | 1〜16 | `MAX_CONCURRENT_JOBS` |
| 同時サムネイル生成 | 2 | 1〜8 | `MAX_CONCURRENT_THUMBNAILS` |
| 同時プレビュー生成 | 1 | 1〜8 | `MAX_CONCURRENT_PREVIEWS` |
| 同時原本準備 | 2 | 1〜8 | `MAX_CONCURRENT_INGEST` |
| 一括追加アセット数 | 1000 | 1〜1000 | `MAX_UPLOAD_ASSETS` |

送信枠は受信中の転送に使い、受信後の変換完了まで占有しません。サムネイル・変換・プレビューは独立した待機列ですが、一つの作品内の必要な処理順は守ります。手動開始の追加枠は通常の上限とは別です。[転送先と手動開始](../manual-start-0250.md)

最初からすべてを最大値にしません。CPUだけでなくメモリー、ディスク速度、一時領域、同時再生の応答を見ながら一項目ずつ調整します。小さいサーバーは変換1〜2件から始めると、他の操作への影響を調べやすくなります。

## 設置環境で指定する値

| 変数 | 用途・既定 |
| --- | --- |
| `HOST` / `PORT` | 直接起動は `127.0.0.1:3000`。標準コンテナ内は `0.0.0.0:3000`。Composeの同名変数はホスト公開側にも使用 |
| `DATA_DIR` | 直接起動はインストール先基準の `./data`。コンテナは `/data` |
| `MEDIA_DIR` | 省略時はdata内。分離時は既存の実ディレクトリ。設定変更前に[移行](../storage.md)が必要 |
| `HTTPS_KEY_FILE` / `HTTPS_CERT_FILE` | Mirea自身でTLSを終端する場合のPEMパス。必ず両方指定 |
| `HEALTHCHECK_CA_FILE` / `HEALTHCHECK_TLS_SERVER_NAME` | コンテナの直接HTTPSヘルスチェックに使うCA・DNS名 |
| `CORS_ORIGINS` | Android同梱画面は `https://localhost`。必要な正確なOriginだけを列挙 |
| `FFMPEG_PATH` / `FFPROBE_PATH` | 信頼できるメディアバイナリの絶対パス。Linux既定は `/usr/bin/ffmpeg` と `/usr/bin/ffprobe` |
| `APP_UPDATES_DIR` | 公開APK・署名済み更新JSONを置く配信ディレクトリ。秘密署名鍵を置かない |
| `APP_UPDATES_SOURCE` | `disabled`で標準のGitHub更新情報取得を無効化。通常は自サーバーと同じ公開版を取得 |
| `SERVER_ADMIN_USER_IDS` | 初期管理権限を補うアカウントUUID。メールアドレスではない。DBで明示変更した権限が優先 |
| `VITE_API_URL` | Android等の初期接続先をWebビルドへ埋め込む値。サーバー実行時の設定ではない |

`.env`には秘密情報が含まれ得ます。全文や `docker compose config` の実値出力を公開Issueへ貼らず、問題の項目だけを伏せ字にして共有します。

## 管理者アカウント

空の新規DBは初期管理者 `admin@example.com` / `ChangeMe` を作成します。メールとパスワードの両方を変更してから利用します。既存DBに同名アカウントがあるだけで管理者へ昇格する仕組みではありません。

以後の権限変更は「サーバー管理 → アカウント」を利用します。本棚の所有者とサーバー管理者は別です。サーバー管理者でも、所属していない本棚の作品を自動的に閲覧できるわけではありません。

設定を戻す場合は変更前の値へ戻します。DBや暗号鍵を削除して初期化しないでください。
