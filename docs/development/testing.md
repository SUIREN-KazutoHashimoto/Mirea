# テストと品質確認

自動テストは実データと分離した一時DB・合成素材を使います。自動テスト、実ブラウザーの画面確認、コンテナ実行、APKビルド、実機確認はそれぞれ確認できる範囲が異なります。

## 準備

[開発環境](setup.md)を用意します。LinuxはFFmpeg/FFprobeが必要です。Web UIテストにはPlaywrightのChromiumを導入します。

```sh
pnpm exec playwright install chromium
```

LinuxでブラウザーのOS依存も入れる場合は `pnpm exec playwright install --with-deps chromium` を使います。OSパッケージ導入が許可された検証機で行ってください。

## テストを選ぶ

| 変更 | 最初の確認 | 広い回帰確認 |
| --- | --- | --- |
| API・権限・DB | 対象の `tests/*.test.js` | `pnpm test` |
| 起動・保存先 | `pnpm test:startup` | コンテナ実起動・再作成 |
| 更新情報・署名 | `pnpm test:updates` | 実署名検証・専用端末での更新 |
| サーバー配布物 | `pnpm test:package` | 配布アーカイブ検査 |
| Web操作 | 関連クライアントテスト、`pnpm build` | `pnpm test:ui` |
| Android | 対象Javaテスト | `testDebugUnitTest lintDebug assembleDebug` |
| 文書 | `pnpm test:docs` | 新規の合成環境で手順を読み通す |

小さい変更では、まず関係する振る舞いを直接検証します。同じ実装をなぞるだけのテストや無関係な大規模テストの反復で結果を水増ししません。例:

```sh
node --test --test-concurrency=1 tests/server-settings-0230.test.js tests/library-history.test.js
```

テスト名の旧版番号は追加時期を示し、現行コードへの回帰検証として使います。失敗時は再現条件を確認し、期待値だけを書き換えて通しません。

## 標準の確認

リポジトリ直下で実行します。

```sh
pnpm test
pnpm build
pnpm test:startup
pnpm test:package
pnpm test:ui
pnpm test:docs
```

`pnpm test` はNodeのテストを1並列で実行します。動画変換・画像検査を含むためCPUと一時領域を使います。

## 画面を確認する

`test:ui` は管理・プレイヤー・ワークスペース・手動転送のスクリプトを順に実行します。新しいブラウザーと合成DBを使い、既存ブラウザーの認証情報には接続しません。

- 管理・転送: `.local/ui-checks`
- プレイヤー: `.local/player-ui-checks`
- ライブラリ: `.local/workspace-ui-checks`
- 手動転送: スクリプトが表示する出力先

成功数だけでなく、PC幅・狭い縦画面・横画面でボタン、モーダル、固定パネル、スクロールを画像で確認します。公開画像も合成素材を使い、個人のタブ・アドレス欄などを含めません。

## Android

`pnpm android:sync` の後、`android` で実行します。

```sh
./gradlew testDebugUnitTest lintDebug assembleDebug
```

Windowsは `.\gradlew.bat` を使います。Robolectricはサービス、Activity、データ処理の回帰を確認しますが、実機デコーダー、メーカー省電力、OSのPiP、Play Protect判定を再現しません。

WebViewの変更時は、同梱UIの起動、bootstrap、禁止した外部コード・bridge、worker経路、旧キャッシュの影響も確認します。Capacitor更新では[固定パッチ](../../patches/@capacitor__android@8.5.3.patch)とnative境界テストを省かないでください。

## コンテナ

通常の作品やアカウントがない専用Composeプロジェクトで行います。CIの手順は [verify.yml](../../.github/workflows/verify.yml) を参照します。

CIは起動保護、メディア変換、高解像度画像本、再作成後のデータ・鍵、異なる保存先間の処理を検査します。`check-container.mjs` 等はfixtureを作成します。運用中のサーバーへ向けて実行しません。

各基盤そのものの検証と、Dockerでその設定条件を再現した検証を区別します。保護を無効にした成功を対応実績にしません。

## 公開旧版からの更新と復元

同じ候補イメージを再作成するテストは、旧版からの更新試験を代用しません。[check-source-upgrade.mjs](../../scripts/check-source-upgrade.mjs) は、指定した旧コミットを `.local` の新しい一時フォルダーへ書き出し、旧サーバーで作成した合成データを候補コードで開きます。現在のチェックアウト、既存の `data`、稼働中のサーバーには接続・書き込みしません。試験用フォルダーだけを終了時に削除します。

旧版のコミットは公開タグと照合してから指定します。次は `v0.25.0beta` の公開コミットを使う例です。Gitとtarが必要です。旧コミットがローカルにない場合は、その公開タグを取得してから実行します。対象版を変える場合も、ブランチのHEADで代用しません。

```sh
git fetch origin tag v0.25.0beta
git rev-parse 'v0.25.0beta^{commit}'
node scripts/check-source-upgrade.mjs --from-commit=91c56352daffe2289392165390ffd36c0889bbe0
```

確認する順序は次のとおりです。

1. 公開旧版の実サーバーコードで、アカウント、親子シリーズ、PDF、進捗、履歴、暗号化ダウンロード、未完了アップロードを作成します。
2. サーバーを停止し、data/media・合成設定を、ファイル時刻の小数部分も保持するPAX形式のtarへ完全コピーします。
3. 候補コードで同じデータを開き、既存セッション、パスワード認証、内容とRange、履歴・進捗、取得済み暗号文の復号を確認します。未完了の転送を再開・完了します。
4. 更新済みデータを上書きせず、別の空フォルダーへバックアップを復元し、旧コードで同じ確認をします。
5. 保存先一体／分離の両方で、ダウンロードの主鍵、ストレージ識別子、バックアップ原本が保持されていることを確かめます。

ここで復元するのは停止中のファイルコピーです。**管理画面で作る暗号化バックアップの生成・復号・復元を、このスクリプトで確認したという意味ではありません。** その試験は[管理画面バックアップの回帰テスト](../../tests/admin.test.js)で分けて行います。管理画面APIでの作成、復号、標準tarによる展開、復元先のサーバーでの既存ダウンロードの再認可・暗号文取得を確認します。

このスクリプトは現在インストール済みのNode依存関係を旧・新コードで共用し、Fastifyのin-process要求で実API・SQLite・ファイル・暗号処理を検証します。公開コンテナのOS・旧lockfile依存、HTTP/TLS境界、署名APKの上書き更新、端末側Keystoreの保持は確認しません。正式公開前には、固定した配布候補についてコンテナまたは完成品アーカイブでの更新・復元と、同じAPK署名による実端末更新を別途行います。

## 実機で確認する項目

| 操作 | 確認すること |
| --- | --- |
| 起動・更新 | 新規と同じ署名の旧版からの更新、データ保持、OS確認 |
| 再生中にホームへ戻る | 再生・通知・ロック画面操作が途切れない |
| PiPへ移る・戻る・閉じる | 二重再生、画面消失、停止状態の食い違いがない |
| Wi-Fi/LTE/到達不能の切替 | 不要な再描画、位置の巻き戻り、長時間固まりがない |
| 保存済み作品を開く | 本体・鍵・期限・アカウントが合えば閲覧できる |
| フォルダ転送中に画面を閉じる | native転送が継続し、取消・再試行が実際の状態に一致 |
| 権限取消・ログアウト | 古い権限で新規取得・操作が継続しない |
| 省電力・回転・Activity再生成 | 画面と再生サービスの状態が一致 |

OS・端末条件は匿名化して記録し、個人の端末名やサーバーの所在は公開しません。

## 結果の書き方

「関連テスト成功」「全体テスト成功」「CI成功」「実機確認済み」を区別します。対象コミット、コマンド、成功・失敗、未確認範囲を対応付け、旧版の検証数を新しいコードの結果として記載しません。
