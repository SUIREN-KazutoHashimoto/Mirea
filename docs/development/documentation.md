# 文書の更新と公開情報の基準

手順書は利用者が目的を達成できること、設計書は変更する人が挙動と制約を判断できることを基準にします。すべてのページを長くするのではなく、詳しい説明へ辿れる構成を保ちます。

## 資料の役割

| 場所 | 内容 |
| --- | --- |
| README | 製品の説明と目的別の入口 |
| docs/install | 準備・構築・接続の手順 |
| docs/user | 利用者の操作 |
| docs/operations | 管理・更新・バックアップ・復旧 |
| docs/reference | 設定値・対応範囲の正本 |
| docs/design / api.md | 実装の責務・状態・データ・API |
| docs/development | 開発・フォーク・テスト・配布 |
| docs/security | 公開できる調査記録 |
| RELEASE.md / 版別ページ | その時点の変更記録 |

現行仕様を複数ページへコピーして増やさず、要点を書いて正本へリンクします。過去のページは歴史資料と明記し、新しい操作へ誘導します。未公開変更は[対象版](../status.md)で区別します。

## 手順書に必要なもの

各手順には、対象読者、完成した状態、前提、実行する場所、操作、成功確認、次の手順を含めます。複数のOSやshellで構文が違う場合は分けます。

コマンドの直前に「どのPC・どのフォルダで実行するか」を書きます。置換が必要な値は明示し、コマンド出力のプロンプトや説明文を一緒に貼らせないようにします。削除・初期化・復元は対象と失うものを操作の前に示します。通常の障害対処をデータ削除から始めません。

初回導入は準備から最初の閲覧まで通して確認します。バックアップ手順は取得だけでなく、空の復旧先への復元と確認までを含めます。

## 設計書に必要なもの

- 責務、呼出し元、公開API、状態と不変条件。
- 正常時の流れと、失敗・取消・再試行・再起動時の流れ。
- DBとファイルの整合、権限、同期、競合、期限、リソースの上限。
- 関連ソースと対応するテスト。
- 採用理由、代替案を選ばなかった理由、変更時に確認する事項。

数値はコードの定義と照合します。DB辞書・API一覧は生成可能な部分を生成し、意味・例外・設計判断を人が補足します。自動生成した名前の一覧だけを詳細設計書の完成としません。

## 公開情報の境界

公開するのは製品の一般仕様、対応する実行基盤、架空の設定例、合成データによる検証結果です。Docker DesktopやTrueNASも一般の導入先として記述できます。誰が実際にどの基盤を使用しているかを結び付けません。

次は公開文書・PR・リリース説明・画像・ログ・同梱ファイルへ含めません。

- 個人の開発/運用ホスト名、内部IP、実ドメイン、CA名、実保存先。
- 利用者やテスターの環境の所在、実作品名、履歴、アカウント情報。
- 鍵・トークン・パスワード・署名設定の秘密値。
- 個別環境への配置状況や、非公開の依頼・会話内容。

個別の運用報告は非公開の会話で伝えます。技術的な識別子として公開済みコードに残る固定名と、現実の導入先を説明する文章は区別します。安全検査の固定値を文書整理のついでに削除しません。

## 例と画像

ドメインは `mirea.example.com`、アカウントは `reader@example.com` のような例を使います。LANアドレスが必要なら実値を記載せず、入力欄の意味と読者自身の値への置換を説明します。IPの説明用には文書用の範囲を使い、到達可能な実サービスであると示しません。

画面は合成作品・専用アカウントで撮影し、OS通知、別タブ、プロフィール、ブックマーク、実URLを含めません。図はMermaid等の差分を追える形式を優先します。

## 変更後の確認

```sh
pnpm test:docs
```

ファイルリンク・ページ内見出し・コードフェンス・公開文書中の典型的な環境情報を検査します。外部サイトの存続や説明の正しさ、画像内の文字までは保証しません。

さらに、変更した操作を初めて使う人の順番で読み直し、記載値をソースと照合します。`test:docs` はスキーマ・API一覧の生成結果との一致も検査します。DBまたはルート登録を変更したら、次で生成表を更新し、意味の説明も見直します。

```sh
node scripts/generate-schema-docs.mjs
node scripts/generate-api-inventory.mjs
pnpm test:docs
```

スキーマ生成は空のインメモリDB、API一覧は静的なソース解析だけを使用します。実サービスへは接続しません。公開前にはPR本文と添付ファイルも同じ基準で確認します。

## 過去の公開内容

現行ファイルを直しても、過去のGit履歴やRelease添付物は変わりません。過去の公開物の修正・削除や履歴の書き換えは、通常の文書更新とは分けて影響を確認します。
