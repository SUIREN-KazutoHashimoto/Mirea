# 閲覧記録・統計の設計

対象は[現行作業ツリー](design/overview.md)です。利用者への説明は[プライバシー](user/privacy.md)、API全体は[API](api.md)を参照してください。実装の中心は[server/analytics.js](../server/analytics.js)です。

## 記録の単位

`analytics_views`は一回の閲覧セッション、`analytics_events`はその中のイベントです。view IDとevent IDはUUID、`seq`はview内の順序です。ユーザー、本棚、アセット、タイトルは認証とDBから解決し、クライアントが任意の別ユーザーの記録として申告できません。

ビューアーとカード上のプレビューは`context`で区別します。先読みは実際の閲覧として記録しません。音声・動画の通常表示、背景再生、PiPも区別します。

|値|意味・制約|
|---|---|
|intervalMs|一つのサンプル区間、最大5秒|
|visibleMs|画面が表示されていた時間、intervalMs以下|
|activeMs|表示・操作の条件を満たす時間、visibleMs以下|
|watchMs|実再生の時間、intervalMs以下|
|backgroundMs / pipMs|watchMsの内数。対応する再生状態が必要で、二つを同時に重複加算しない|
|fromMs / toMs|メディア時間軸上の移動範囲。時計上の視聴時間とは別|
|gapMs|タイマー停止等で連続性を確認できない時間|
|page等|実際の読書ページ・位置。先読みしたページを読了として送らない|

一般的な約1秒サンプルでも、OS停止後の巨大な時間差を視聴時間へ一括加算しません。シーク中、バッファ待ち、表示していないプレビューの時間を視聴として認めません。サーバーは時間の大小関係や状態の整合を検査し、不正な区間を422にします。

## 再送と保持

POST `/analytics/events`は一度に50イベント、64 KiBまで、ユーザーごと毎分240要求を上限にします。同じイベントID・内容hashの再送は重複計上せず、同じIDに別内容を送ると409です。Web／Androidは接続先とユーザーを分けて送信待ちを保ち、通信失敗時も同じIDを使います。

通常の生イベントには自動保存期限を設けません。`retentionDays:0`は即時削除ではなく無期限です。収集を停止しても既存記録は削除しません。アセットの削除や共有解除でも、既に発生した本人の記録は直ちには削除しません。アカウント削除は専用処理で本人の記録を削除します。

閲覧履歴の「非表示」は`history_hidden`のcutoffを使い、生統計や続き位置とは分けます。再び閲覧すると履歴に戻せます。履歴一覧にはprivate本棚のアセットを表示しません。

## 本人の詳細と匿名集計

|取得者|取得できる情報|
|---|---|
|本人|自分の詳細集計・生イベント。期間、アセット等で絞り込める|
|本棚所有者|本棚の匿名集計。個人別の生イベント取得APIではない|
|サーバー管理者|全体の匿名集計。管理権限だけで他人の本人用APIを呼べない|
|サーバーOS管理者|DB／バックアップへ直接アクセスできる。これはUIの匿名化境界の外側|

本人の生イベントはrow cursorによるページ取得です。JSONは`events,nextCursor,hasMore`、NDJSONは`X-Next-Cursor`を返します。1ページ上限は1,000件です。cursorは応答を使い、イベント時刻だけをカーソルとして推定しません。

匿名集計は7日／30日／90日／全期間の固定期間です。UTC当日を除外し、出力するグループごとに異なる利用者が5人以上いる場合のみ表示します。人数／回数は5単位、時間は10秒単位で切り下げます。個人や細かい時刻を指定するqueryは拒否します。アセット最大1,000、ページ／動画区間最大5,000を超えると`truncated`で示します。

この仕組みは少人数の推測を減らすための制限で、差分プライバシーの数学的保証ではありません。生DBとバックアップは利用者の閲覧情報を含むため、公開ログ、CI、共有添付へ入れません。

## 再生頻度との違い

動画の頻度グラフは、生イベントから3秒以上の連続視聴だけを抽出した別の投影です。一般のwatchMsや生イベントを消すための規則ではありません。匿名表示が成立しない場合の本人だけのグラフを、他人の少人数集計で埋めることもしません。[再生頻度グラフ](video-replay.md)に詳述します。

## 変更時の確認

イベントschemaを変える際は、旧クライアントの再送hash、区間検証、背景／PiPの内数関係、重複・順序遅延、アカウント切り替え後の送信先、履歴非表示と原記録の独立性を確認します。集計の表示制限を変える場合はprivacy応答と利用者への説明も更新します。
