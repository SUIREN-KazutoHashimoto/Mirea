# 0.16.0beta — 運用変更と検証範囲

## 更新する前に

サービス停止中にdata全体、分離配置ならmedia全体、設定、AD CS証明書を同じ時点でバックアップしてください。DBはv19へ追加型移行します。旧バイナリだけに戻さず、旧コードと更新前バックアップを組で戻します。既存アカウント、個人の生ログ、進行度、暗号化鍵、APK署名、証明書を変更・削除しません。

Codexの再現・詳細なログ取得・検証はWinVAI01 LANだけで行います。TrueNASはベータテスターの常用・実機テスト環境で、個人アセットを診断に取り込みません。イメージの公開はNASの更新操作を実行しません。

## 転送と後処理

- 送信枠は分割データの受信完了・サーバー受付で解放し、変換を待たず次を送ります。Androidも後処理の監視を送信ワーカーから分離します。
- 同時送信は利用者ごと、後処理はサーバー全体の上限です。管理者メニュー「転送・後処理設定」で保存し、パスワード確認を要求します。変更は待機・新規処理に適用し、実行中の処理は強制停止しません。
- 初期値は同時送信3件、同時後処理5件、一括選択1000アセット。設定範囲は順に1〜32、1〜16、1〜10000。環境変数の初期値は`MAX_CONCURRENT_UPLOADS`、`MAX_CONCURRENT_JOBS`、`MAX_UPLOAD_ASSETS`で指定できます。管理画面で保存した値を優先します。
- 上限到達時は待機し、429だけでバッチ全体を失敗させません。認証・権限エラーでは送信を止めます。1アセットの容量上限`MAX_UPLOAD_BYTES`、画像・EPUBの上限は別設定です。
- 複数フォルダは「フォルダを丸ごと選択」を繰り返して追加し、同じキューでまとめて送れます。OSのフォルダ選択は1回1ルートの機種があります。空フォルダは含まず、16階層・300フォルダまでです。
- 転送画面を閉じても処理を継続します。ただしブラウザーの終了・OSの強制停止まで保証するものではありません。再選択時は分割ハッシュを確認して再開します。
- 明示キャンセルでは未完了の処理を停止し、原本と分割データを回収します。完了分は追加確認してから削除します。フォルダ取込で新規作成した空シリーズだけを回収し、再利用したシリーズ、他の作品が入ったシリーズは残します。ログアウト・サーバー切替・OS停止は原本削除を伴う明示キャンセルと区別します。

## シリーズと履歴

シリーズ名は同じ本棚・同じ親の中で一意です。異なる親では同名を許可し、フォルダ取込では既存パスを再利用します。既存重複の自動改名・統合・削除はしません。既存の重複は管理者の確認が必要です。

再帰削除は子シリーズ・作品・未完了アップロードの件数を確認し、配下の削除を明示選択した場合だけ実行します。確認後に対象が変わったら拒否します。シリーズだけ削除する場合は作品を残しますが、子の移動先で同名になる場合は先に整理してください。一括移動は同じ本棚内、循環・16階層超過・名前の重複は禁止です。

本棚のプライベートフラグは「すべてのコンテンツ」から隠す表示設定で、共有・認可の仕組みを変更しません。本棚を直接選ぶと表示でき、明示的に作った個人プレイリストや閲覧履歴には残ります。

履歴の削除は本人の一覧から隠すだけです。生ログ、統計、進行度、作品や鍵は削除しません。既存セッションのheartbeatでは再掲せず、その後に新しい閲覧セッションを受信した作品を再掲します。

## 表紙とオフライン一覧

動画は40〜60%の区間のランダムな時刻を選びます。1秒未満の映像は実際に存在するフレームを使います。配信表紙は長辺1024px以下・縦横比を維持・拡大なしのWebPで、元メディアと元画像は保持します。旧JPEGも残し、必要時にWebPを作成します。

一覧・表紙の保存は取得の再試行と最大2MiBの画像に対応します。失敗件数を表示し、再実行できます。メディア本体は別途明示ダウンロードが必要です。端末の実容量・OSのストレージ回収の影響は残ります。暗号化、アカウント分離、オフライン許可7日間を緩和しません。

## APK自動更新

通常のサーバー起動では、`APP_UPDATES_DIR`が未設定なら、そのサーバーと同じ公開リリースの`mirea-android-update.json`をGitHubから取得します。署名と期限を検証し、同じリリースの公開APK以外のURLは拒否します。Androidは引き続き保存済みのMireaオリジンへ確認し、APKを取得してハッシュ・APK署名・版番号を検証します。秘密鍵は配布用PCの外部保管先に留め、NAS・イメージ・CIへ入れません。

NASにはGitHubへのHTTPS疎通が必要です。`APP_UPDATES_DIR`を設定済みならローカルの署名済みバンドルを優先します。`APP_UPDATES_SOURCE=disabled`は公開リリースからの取得を無効にします。失敗時はエラーとして閉じ、TLS・署名・期限の検証を無効にしません。

**署名付き更新情報は最大7日間有効**です。公開後も同じAPK・versionCode・ハッシュのまま再署名が必要です。期限を延ばすためにAPKを作り直したり、同じversionCodeへ違うAPKを差し替えてはいけません。署名者の定期更新が止まった場合は自動更新も停止し、再署名または公式リリースAPKの手動上書きが必要です。

## 初期管理者

ユーザーが1人もいない新規環境だけ、`admin@example.com` / `ChangeMe`を作ります。既存環境に追加したり、既存アカウントを管理者に昇格したりはしません。メールとパスワードの両方を変更するまで管理操作を拒否します。外部公開前に必ず変更してください。

## Playプロテクト調査

0.14.0betaと0.15.3betaのソース比較では、AndroidManifestの権限、更新機構、network_security_config、SDK設定に差分はなく、app/build.gradleのversionCode/versionNameだけが変わっています。これだけではGoogle側の警告理由を断定できません。今回のAPKが端末上で警告解除されたことも未確認です。

警告の詳細文言・検知対象のAPKハッシュ・インストール元・端末/Playプロテクトの版が必要です。個人アセットや閲覧記録は不要です。公式の[警告ガイド](https://developers.google.com/android/play-protect/warning-dev-guidance)と[再審査手順](https://support.google.com/googleplay/android-developer/answer/2992033)に従い、まず原因とポリシー適合を確認します。保護機能の無効化、署名やパッケージ名の変更による回避、未確認の誤検知断定は行いません。外部への再審査申請は所有者の承認を得てからです。
