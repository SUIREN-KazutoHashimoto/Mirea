# サーバー管理

対象: Mirea `1.0.0`。

サーバー管理者はメニューから「サーバー管理」を開きます。作品を管理する本棚所有者と、サーバー全体を管理する管理者は別の権限です。管理者になっても他人の本棚の閲覧権限は自動付与されません。

## 最初の管理者を準備する

アカウントが一つもない新規環境では、`admin@example.com` / `ChangeMe`を作成します。初回ログイン後にメールアドレスとパスワードを両方変更します。どちらかが初期値のままなら管理操作を許可しません。既存環境の起動や更新で、このアカウントを追加し直すことはありません。

管理者が既にいる場合は、その管理者がアカウント管理から権限を変更します。導入時の補助として`SERVER_ADMIN_USER_IDS`にカンマ区切りのUUIDを指定できますが、DBに明示的な権限があるアカウントではDBの権限を優先します。これは一般の設定値に対する「環境変数優先」とは別の、権限の初期指定です。メールアドレスを指定する変数ではありません。

最後の有効な管理者の停止・権限解除・削除は禁止します。管理者にアクセスできなくなった場合、バックアップと実行中の保存先を確認して保守担当者へ連絡します。DBの削除や初期アカウントの作り直しを復旧策にしません。

## 管理画面でできること

| 画面 | 用途 |
| --- | --- |
| 概要 | 稼働版、保存容量、サーバー状態の確認 |
| ジョブ管理 | 実行待ち・実行中、履歴、未完了アセットの修復、再生成 |
| 処理の設定 | 転送・後処理の同時数、一括追加数 |
| サーバーの設定 | アセット容量上限、分割サイズ、登録・記録の可否 |
| アカウント | 作成、権限変更、停止・再開、削除 |
| 本棚の権限 | 所有者・共有状態の管理 |
| ファイル整理 | 参照されないメディア等を確認して削除 |
| バックアップ | 暗号化したメタデータ／全体バックアップ |
| サーバー更新 | 配布情報と更新可否の確認 |
| エラー報告 | 利用者が送信した安全な診断情報を送信単位で確認・コピー |
| 管理操作の記録 | 管理者による変更の確認 |
| データのリセット | アカウントを残す全メディア削除 |

## ジョブを確認・やり直す

1. 「現在のジョブ」を開き、検索・状態・並び替えを使って対象を探します。
2. 件数が多い場合はページを移動します。表示中の行数と、待機列全体の件数を混同しません。
3. 行を選び、種類、進捗、経過時間、推定終了時刻、エラーを確認します。推定時間は確定した完了時刻ではありません。
4. 完了・失敗・取消は「履歴」で確認します。履歴の存在と、現在そのアセットが存在することは別です。
5. 出力が欠けている、失敗後に変換待ち表示が残る場合は「アセットの再生成」の未完了アセット対象を使います。まず対象確認を行い、正常なものや処理中のものが含まれていないか確認します。

アップロード受信、取り込み、表紙、トランスコード、プレビューは段階と実行枠が分かれています。待機列はDBへ保存し、再起動時には未処理分を復旧します。同時数は[処理の設定](operations/settings.md)で調整します。大量の待機ジョブがあっても、画面に並ぶ行数が並列数ではありません。

手動開始できる待機ジョブには開始操作が表示されます。通常の実行上限とは別の手動枠を使い、同時に無制限に開始するものではありません。強制開始もCPU・メモリー・保存容量を必要とします。

### 再生成の選び方

| 対象 | 用途 |
| --- | --- |
| 未完了のアセット | 失敗・不足した出力を修復したい |
| 一つのアセット | 表紙や動画出力を個別に作り直したい |
| 全アセット | 全体の出力を意図的に作り直したい |

カスタム表紙はアップロードした原本から再生成します。動画からの自動表紙へ勝手に戻す処理ではありません。一般ユーザーも、所有する対象アセットの表紙再生成を利用できます。

再トランスコードは保持原本を優先します。原本がなければ利用可能な配信用データを使うため、失った品質は復元できません。既存の配信世代が保持される場合があり、再生成前に空き容量を確認してください。

個別・一括の再生成には管理権限と処理コストの確認が必要です。削除や権限変更、バックアップなどに必要なパスワード再確認を省略する機能ではありません。

## アカウントと本棚の権限

- アカウントの権限変更、停止、メールなどの重要変更ではセッションや配信チケットを失効させます。変更後に再ログインが必要になる場合があります。
- 所有本棚があるユーザーを削除する前に、必要な本棚の所有者を変更します。
- 他人の既存パスワードを管理者が既知の値へ置き換えて利用する運用はしません。本人の変更手順を使います。新規作成の初期パスワードは本人へ安全に伝えます。
- 管理操作は監査記録へ残します。アカウント管理は、個人の詳細な閲覧履歴を読む権限ではありません。

閲覧統計の匿名化ルールは[分析とプライバシー](analytics.md)を参照してください。利用者が送信した診断情報には、安全なエラー詳細を用います。通常ログが必要な場合も、問題時刻とエラーIDの範囲に絞ります。

## ファイル整理

これは容量確保のための明示操作です。画面を開くだけでファイルを削除しません。

1. 候補をスキャンします。
2. 「有効な所属者がいない本棚のアセット」と「DBから参照されない残存ファイル」を区別します。
3. 権限の修正やアカウント再開で戻せる作品は、削除する前に復旧を検討します。
4. 不要な候補だけを選択し、管理者パスワードと確認文字列`DELETE`で削除します。
5. 結果を確認し、I/Oエラーがあれば保存先を直して再スキャンします。

候補は時限の確認情報であり、削除直前に参照とファイル状態を再検証します。途中・失敗原本、稼働中ジョブ、DB・鍵・バックアップは安易な削除対象にしません。リンクや特殊ファイルを追跡しません。必要なら先に[全体バックアップ](operations/backup-restore.md)を取得します。

## バックアップ、更新、全削除

- [バックアップと復元](operations/backup-restore.md): パスワード、全体／メタデータの違い、取得期限、復元先を確認します。
- [更新と復帰](operations/updates.md): コンテナはホスト側で更新します。MireaへDockerソケットを渡しません。
- [データのリセット](admin-reset.md): 全利用者のメディアを消す別操作です。通常の不具合対処として実行しません。

OS固有の特権保守ヘルパーは、その環境に合わせたレビューと復旧訓練が必要です。リポジトリ内の専用スクリプトを汎用インストーラーとして実行しないでください。

実装: [admin.js](../server/admin.js)、[管理権限](../server/admin-access.js)、[ジョブ](../server/admin-jobs.js)。
