# 運用メモ

サーバーはNode.jsの直接起動とDocker起動の両方に対応します。[起動方式ごとの設定・データ切替](run-modes.md) を参照してください。機能は共通で、起動方式の切替だけならWeb／Androidクライアントの変更は不要です。

## サーバー設定

| 環境変数 | 初期値 | 意味 |
| --- | --- | --- |
| HOST | 127.0.0.1 | 直接起動の待ち受け／Composeのホスト側公開アドレス。コンテナ内は0.0.0.0 |
| PORT | 3000 | 直接起動の待ち受け／Composeのホスト側公開ポート。コンテナ内は3000 |
| HTTPS_KEY_FILE / HTTPS_CERT_FILE | 未指定 | 直接HTTPSの秘密鍵・証明書チェーンのPEM。必ず両方指定。相対パスはインストール先基準 |
| DATA_DIR | ./data | 直接起動の保存先（インストール先基準）。通常のComposeはnamed volumeを/dataへマウント。host-data追加設定ではホスト側パス |
| CORS_ORIGINS | https://localhost | Androidなどの許可Origin。カンマ区切り |
| MAX_UPLOAD_BYTES | 2147483648 | 1コンテンツ合計の上限、2 GiB |
| UPLOAD_CHUNK_BYTES | 8388608 | 独立したPUTの分割サイズ、標準8 MiB |
| FFMPEG_PATH | ffmpeg-staticの同梱バイナリ | 動画サムネイルに使うFFmpegの絶対パスを上書き |
| ALLOW_REGISTRATION | true | falseで新規登録を停止 |
| VITE_API_URL | 未指定 | Androidの初期接続先。Webビルド時に適用 |

Androidは `https://localhost` OriginからリモートAPIに接続するため、CORSの初期値を保持します。PC WebはAPIと同一のサーバーから配信します。APIを別ドメインに分ける構成は初期版の対象外です。

直接起動はインストール先の `.env` を自動で読み、OSの明示的な環境変数を優先します。Composeは同じ `.env` から必要な値だけを渡し、コンテナ内の待ち受けと保存先はDockerfileの固定値を維持します。ホストのFFmpegパスなどはコンテナへ渡しません。

## HTTPSでAndroidから接続する

Nodeの直接HTTPSも利用できます。`.env` へ `HTTPS_KEY_FILE` と `HTTPS_CERT_FILE` を設定してください。片方不足・読めないファイル・不正なTLS設定は起動失敗とし、HTTPへ戻しません。LANの自己署名運用は [LAN HTTPS](lan-https.md) を参照してください。AndroidはシステムCAに加え、端末利用者が明示的に導入したユーザーCAを信頼します。証明書・ホスト名検証やHTTP禁止は維持します。

直接起動サーバー／コンテナの前にCaddyやnginxを置き、信頼できる証明書付きのHTTPS URLを用意します。同じホストでCaddyを使う場合の最小例:

```caddyfile
mirea.example.com {
    reverse_proxy 127.0.0.1:3000
}
```

Caddyは別途インストールして起動します。ドメインのDNSと80/443番ポートの転送が必要です。標準のアップロードUIは独立した8 MiBのPUTを使います。nginxなどでも、そのサイズのPUTと `X-Chunk-SHA256` を許可してください。合計上限2 GiBと1リクエストの上限は別です。従来のmultipart APIを直接利用する場合は、全量1リクエストで受信するので別途上限・時間を揃える必要があります。

自前サーバー＋Cloudflare Tunnel／Proxyの設定と動画配信条件は [Cloudflare運用メモ](cloudflare.md) にまとめています。公開Tunnelだけで動画配信の条件を満たすとは限りません。

アクセスログには動画チケットを含むクエリ文字列を記録しない設定にしてください。APIはプロキシ由来の任意のX-Forwarded-Forを信用しないため、プロキシ背後では認証レート制限がプロキシIP単位になります。多数の利用者向け運用では、信頼するプロキシを固定した設定と入口側のレート制限を追加してください。

閉じた利用なら利用者の登録後に `.env` の `ALLOW_REGISTRATION=false` とします。コンテナは `docker compose up -d`、直接起動は停止して `pnpm start` で反映します。メール確認を実装していないため、登録されたメールアドレスの所有確認は行いません。

## バックアップと復元

整合性を保つため、サーバー停止中にデータ領域全体（SQLite本体・WAL・SHM・uploads・thumbnails・keys）をバックアップします。画像の本は `uploads/books/<UUID>/`、サムネイルは `thumbnails/<UUID>.jpg` に保存されます。暗号化ダウンロードの `keys/download-master.key` は必須で、失うと既存の端末保存データを復号できません。登録があるのに鍵が無い場合は起動を拒否します。DBと同時点の鍵を復元してください。[詳細](downloads.md)。初回アップデート前にもバックアップを取得してください。

動画プレビューは必要時に `previews/<UUID>.mp4` へ生成します（各最大2 MiB）。ここは再生成可能な派生キャッシュで、バックアップに含めなくても本編・画像サムネイルは保持されます。容量を回収する場合はサーバー停止中にこのキャッシュだけを対象とし、uploads・SQLiteを削除しないでください。次回の要求時に再生成します。詳細は [動画プレビュー仕様](video-previews.md) を参照してください。

直接起動では `Ctrl+C` 等で停止し、`DATA_DIR` 全体をバックアップしてから `pnpm start` で再開します。コンテナの例:

```sh
docker compose stop mirea
# Dockerのボリュームバックアップ手順に従い、mirea-data全体を保存
docker compose start mirea
```

復元もサーバーを停止して行い、DBとファイルを同じバックアップ時点の組み合わせで戻します。UID 1000（コンテナのnodeユーザー）が書き込み可能な所有権にしてください。バックアップにはアカウント・セッション・個人のメディアが含まれるため、アクセスを制限します。

分割受信データは `uploads/transfers/<UUID>/` に置き、`upload_sessions` と `upload_parts` に受信状況を保持します。24時間以内の通信失敗は再開できます。完了・取消・処理失敗では回収し、期限切れは起動時と30分ごとに回収します。結合とサムネイル生成の間は分割データと結合済みファイルが共存するため、同時アップロード合計のおよそ2倍以上の空き領域と、サムネイル／DB分の余裕を見込んでください。

強制停止で残った `uploads/staging/<UUID>/` や、DBにないUUIDのメディア・画像本ディレクトリ・サムネイルは、**サーバー停止中**にDBのitems一覧と `upload_sessions` 一覧の両方を照合して回収してください。処理中ジョブは次回起動で再構成するため、対応するtransfersを先に消さないでください。稼働中のディレクトリを手動削除しません。

画像は1枚25 MiB・4,000万画素・1冊500枚までです。サムネイル生成と画像デコードには最大30秒、WorkerのV8ヒープには256 MiBの上限があります（ネイティブ画像ライブラリのメモリはこのヒープ上限の対象外）。同時デコードは直列化しています。大量ページの本は保存完了まで時間がかかります。

## 現在の運用範囲

初期版の想定は、信頼する利用者で共有する単一サーバーです。分割アップロードはアカウント当たり同時3件に制限し、生成ジョブは直列処理します。互換multipart APIはこの同時数制限の対象外なので、広く公開する入口では必要に応じてそのPOSTを制限してください。保存領域はファイル上限とは別に容量監視が必要です。ユーザー別の容量制限、全体の容量予約、監査ログ、ウイルススキャン、メール確認・パスワード再設定はまだ実装していません。Web UI・APIとも、アカウントが紐付いていない本棚のコンテンツへのアクセスを拒否します。

## 検証状況

開発環境ではAPIの自動テストとWebのビルド、ブラウザでの操作を検証します。DockerビルドとAndroid APKのビルドには、それぞれDockerおよびJDK / Android SDKのある環境が必要です。ソースの生成・同期成功と、端末上での動作成功は別々に確認してください。
