# コンテナのstable／betaチャネル

イメージは `ghcr.io/suiren-kazutohashimoto/mirea` から取得します。Gitタグと版番号付きイメージは固定し、追従用の2タグだけを更新します。

| イメージタグ | 対象 |
| --- | --- |
| `stable` | 公開済みの最新正式版（Gitタグ `vX.Y.Z`、GitHub Releaseのpre-releaseは無効） |
| `beta` | 公開済みの最新ベータ版（Gitタグ `vX.Y.Zbeta`、pre-releaseは有効） |
| `0.15.3beta` などの版番号／`sha-<commit>`／digest | その検証済みイメージに固定。再ビルドで別内容へ差し替えない |

正式リリースがまだない間は `stable` を作りません。ベータ版を便宜上 `stable` として配布することもありません。`latest` は使いません。チャネル切り替えがDBのダウングレードを許可するわけではなく、現在のDBより古い版へ戻す場合は更新前データも復元してください。

## GitHub側の更新条件

1. リリース用コミットを `develop` へマージし、そのコミットの正式CI成功を待つ。
2. `package.json`、Dockerfileの版番号、APK、配布リンクを一致させ、新しい版番号のGitタグを作成。既存タグを付け直さない。正式版のpackageは `X.Y.Z`、ベータ版は `X.Y.Z-beta`。
3. タグのWeb/API・コンテナ・Android検証が正式に成功した後、コンテナ公開ジョブが**実際に検証した同一イメージ**をGHCRの版番号タグへ登録し、ドラフトReleaseへ検証情報・アーカイブを添付する。
4. 配布物・バックアップ・適用先での確認を終えてReleaseを公開する。ベータ版だけpre-releaseを有効にする。
5. Release公開イベントで `promote-release-channel` が起動。公開状態、チャネル、最新の版番号、Gitタグ／コミット、コンテナのメタデータ・digest・非root実行・全正式CIを再確認して、該当する追従タグだけを更新する。

正式版の公開で `beta` は動かず、ベータ版の公開で `stable` は動きません。公開日時ではなく数値の版番号で各チャネルの最新を選ぶため、古いReleaseの再公開で巻き戻しません。同じ版番号なのにdigestが変わった場合も停止します。既存betaワークフローと同じ排他ロックを使い、同時実行による上書きを防ぎます。古いReleaseを変更・削除して更新を強制しないでください。

公開済みReleaseのチャネル反映だけを再試行する場合は、GitHub Actionsの **Verify Mirea → Run workflow** でブランチを `develop`、`tag` を公開済みのGitタグ（例 `v0.15.3beta`）にします。正式版を選ぶのは実際に公開済みの `vX.Y.Z` がある場合だけです。この操作は新しいイメージをビルドせず、最新でないReleaseはスキップします。CIやReleaseの公開条件は再試行でも省略しません。

## TrueNAS側の運用

Custom AppのRepositoryを `ghcr.io/suiren-kazutohashimoto/mirea`、Tagを `beta` または、初回正式版の公開後に `stable` としておくと、版ごとのタグ書き換えは不要です。今回の変更でNAS設定は自動変更しません。

追従タグの変更だけで稼働中コンテナが入れ替わるわけではありません。NAS側で新イメージを取得・再デプロイする更新操作が必要です。MireaへDockerソケット・NAS管理資格情報・特権を与えたり、無人更新エージェントを追加したりはしません。

更新前にアップロード／ジョブを完了させて停止し、`DATA_DIR` 全体、分離時は `MEDIA_DIR` も含め、Custom App設定・環境変数・証明書をバックアップしてください。更新前の版番号とdigestを記録し、復旧時はそのイメージと対応する更新前データを一緒に戻します。詳細は[TrueNAS手順](truenas-25.04.md#6-バックアップ更新復帰)を参照してください。
