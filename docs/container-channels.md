# コンテナの固定タグとstable／beta

対象: Mirea `1.0.0`。以下は配布タグの選び方と公開処理の仕様です。実際の公開状態はGitHub Releasesで確認してください。

配布先は`ghcr.io/suiren-kazutohashimoto/mirea`です。初めて導入するときは[GitHub Releases](https://github.com/SUIREN-KazutoHashimoto/Mirea/releases)で公開状態と配布物を確認します。

| タグ | 意味 |
| --- | --- |
| `1.0.0`などの版番号 | 選んだ版を固定して使う |
| `sha-<commit>`、`@sha256:<digest>` | 特定の検証済みイメージを識別する |
| `beta` | 公開済みの最新ベータ版へ追従する |
| `stable` | 公開済みの最新正式版へ追従する |

正式版が存在しない間は`stable`を作りません。ベータを代わりに正式版として扱わず、`latest`も使いません。番号付きGitタグとイメージは内容を差し替えず、追従用タグだけを更新します。

1.0.0の公開では`stable`を正式版へ向けます。既存の`beta`利用者は自動移行しません。正式版へ移る場合は`1.0.0`または`stable`へ明示的に変更します。メジャー0のAPK更新情報の定期再署名は1.0.0公開後に終了するため、サーバーとアプリを同じメジャーへ移行してください。[移行手順](operations/updates.md#ベータ版から正式版へ移るとき)

## タグを決める

確実に版を選んで運用するなら固定タグを使います。管理ツールからイメージ更新を検出したい場合は追従タグを選べます。ただしタグが更新されても、稼働中のコンテナが自動で入れ替わるわけではありません。

Docker Compose、Docker Desktop、TrueNASなど、導入した基盤で新イメージを取得してコンテナを再作成します。再起動だけで新イメージが取得されるとは限りません。TrueNASではPull Policyと更新検査も確認します。[更新手順](operations/updates.md)

## 公開時に確認すること

1. リリースコミットを`develop`へマージし、そのコミットの正式CI成功を確認します。
2. package、コンテナラベル、APK、配布リンク、番号付きGitタグの版を一致させます。
3. タグの正式CIで検証した同一イメージを番号付きタグへ公開し、配布物とメタデータをドラフトReleaseへ添付します。
4. 配布確認後にReleaseを公開します。ベータ版のみpre-releaseにします。
5. 公開イベントのチャネル処理が、公開状態・数値版・Gitコミット・CI・digest・イメージの版ラベルと非root設定を再検証して該当タグを進めます。

正式版の公開は`stable`だけ、ベータ版の公開は`beta`だけを対象にします。公開日ではなく数値の版番号で選ぶため、古いReleaseの再公開で巻き戻りません。同じ版でdigestが変わる場合も拒否します。

チャネル反映だけの再試行は、GitHub Actionsの`Verify Mirea`を`develop`から手動実行し、対象の公開済みGitタグを入力します。これは新しいイメージを作り直す操作ではなく、公開条件を満たす最新の対象だけを反映する操作です。

実装: [チャネル公開処理](../scripts/publish-container-channel.mjs)、[公開条件](../scripts/container-channel-policy.mjs)、[CI](../.github/workflows/verify.yml)。

## 更新前と復帰時

更新前の版・digestを記録し、[全体バックアップ](operations/backup-restore.md)を取ります。分離していればdata/media両方と、設定・証明書が必要です。

チャネルを変えるだけではDBのダウングレードを許可しません。古い版へ戻す場合は旧イメージと対応する更新前データを一緒に戻します。MireaへDockerソケットや基盤の管理者資格情報を渡しません。
