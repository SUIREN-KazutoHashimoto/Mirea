# 保存先の分離と移行

対象: Mirea `1.0.0`。Node.js直接起動とコンテナの両方に適用します。

`DATA_DIR`と`MEDIA_DIR`を別々のディスクへ割り当てられます。ユーザー情報と作品のメタデータは一つのSQLite DBで管理し、DB自体を二つに分けるものではありません。

| 保存先 | 内容 | 選び方 |
| --- | --- | --- |
| `DATA_DIR`（コンテナでは`/data`） | DB・WAL/SHM、アカウント・権限、本棚・シリーズ・作品情報、記録・続き位置、暗号鍵、サムネイル・カスタム表紙の原本、プレビュー、管理ジョブ、管理バックアップ | ローカルSSDなど、低遅延で信頼できる保存先 |
| `MEDIA_DIR`（コンテナでは`/media`） | 原本、再生用動画・音声、HLS、書籍、分割アップロード・受信／変換途中データ | 必要な容量と持続転送速度を持つ保存先 |

`MEDIA_DIR`を省略するとメディアも`DATA_DIR`内に保存します。後から設定値だけを追加しても既存データは移りません。

`DATA_DIR`には記録やバックアップも増えます。ディスク容量は原本だけでなく、派生データ・旧配信世代・転送途中・スナップショット・バックアップの余裕を含めて見積もります。SQLiteのWALは同じホストのローカルストレージを前提とするため、DBをSMB/NFS共有へ置きません。[SQLiteの制約](https://sqlite.org/wal.html)

## 新規導入で分ける

1. 空の専用保存先を二つ作ります。実行UID/GIDが読み書きでき、親ディレクトリを通過できるようにします。
2. 一般ユーザーの共有フォルダーとは分けます。すべての利用者に権限を広げる必要はありません。
3. 直接起動では二つの絶対パスを設定します。コンテナではそれぞれ`/data`と`/media`へマウントし、`DATA_DIR=/data`・`MEDIA_DIR=/media`にします。
4. 二つの実パスを入れ子にしたり、シンボリックリンクで分離したりしません。
5. 起動後に小さな検証用作品を追加して、閲覧・表紙・保存・停止再開を確認します。

`MEDIA_DIR`のルートは先に作成／マウントしてください。初回の分離は、DBがまだなく、メディア側が空の場合だけ受け付けます。

Dockerの新規導入例:

```sh
docker compose -p mirea -f compose.release.yaml -f compose.storage.yaml config --quiet
docker compose -p mirea -f compose.release.yaml -f compose.storage.yaml up -d --wait
```

停止・再開も同じプロジェクト名と二つの`-f`を使います。[Docker](install/docker.md)と[TrueNAS](install/truenas.md)に具体的なマウント手順があります。

## 既存の単一保存先から分ける

**既存環境へ二つのマウントを追加するだけでは移行できません。**

前提はサーバー停止済み、全データと設定のバックアップ済み、新しいメディア保存先が空であることです。スクリプトはこれらの確認フラグを要求しますが、フラグが実際の停止・バックアップを代わりに行うわけではありません。

1. 転送とジョブを完了させ、Mireaを停止します。コピーと設定変更が終わるまで旧・新サーバーを起動しません。
2. `DATA_DIR`全体と設定を[バックアップ](operations/backup-restore.md)します。復元できる場所へ保管します。
3. 同じ版の移行スクリプトを、保存先へアクセスできる非rootの保守ユーザーで実行します。Node.js 24を使います。
4. 以下のパスを実在する保存先へ置き換え、リポジトリのルートで実行します。

Linuxの例:

```sh
node scripts/prepare-media-storage.mjs --data-dir=/srv/mirea/data --media-dir=/srv/mirea/media --acknowledge-stopped --acknowledge-full-backup
```

PowerShellの例:

```powershell
node scripts/prepare-media-storage.mjs --data-dir=C:/Mirea/data --media-dir=D:/Mirea/media --acknowledge-stopped --acknowledge-full-backup
```

5. 成功表示を確認してから`MEDIA_DIR`を設定し、両ルートをマウントして起動します。
6. 元からあった作品・鍵・続き位置が使えることと、新しい作品が追加できることを確認します。
7. 旧メディアは自動削除されません。検証とバックアップ後に管理者が整理します。

コンテナにも`/app/scripts/prepare-media-storage.mjs`を含みます。ホストにNode.jsを用意しない場合は、停止したサービスと同じイメージ・UID/GIDで両領域を一時保守コンテナへマウントする方法があります。保存先が異なるため、通常の起動コマンドをそのまま流用せず、マウントを管理者がレビューしてください。

### ツールが行うことと失敗時の扱い

`uploads`・`videos`・`originals`を新領域へコピーしてSHA-256を照合します。DBと鍵は移さず、元メディアも消しません。DB整合性、処理中のアップロードや管理ジョブ、リンク・特殊ファイル、非空の移行先を検査し、不適切なら中止します。

中断して移行先に一部コピーが残った場合、上書きで続行しません。元データを保持して結果を確認し、別の空の移行先でやり直します。エラーを避けるために識別ファイルを削除しないでください。

## 保存先の識別ファイル

`DATA_DIR/storage-layout.json`と`MEDIA_DIR/.mirea-media.json`は、二つの保存先の対応を示します。マウント漏れ、別インスタンスのメディア、分離ON/OFFの不整合を検出すると起動を止めます。

これらは設定を強制するために手編集するファイルではありません。分離済みの領域を別ディスクへ移すときも、サーバーを停止し、識別ファイルを含めた両領域を同じ時点でコピーします。相互に対応するバックアップとマウントを復元してください。

## バックアップと復帰

管理画面の全体バックアップは、分離した内容を論理的な一つの`data/`へまとめます。復元時はまず単一保存先として戻し、必要なら停止中に上のツールで分けます。メタデータのみでは作品本体は復元できません。

ファイルシステムのバックアップでは両ルートと設定の時点を揃えます。旧版へ戻す場合も、旧コードと対応するデータ・設定を組にします。分離をOFFへ変えて古いコピーを再開すると、移行後の変更を失います。[バックアップと復元](operations/backup-restore.md)

分離環境の更新はホスト側で行います。単一保存先を前提とする専用更新ヘルパーを流用しません。MireaへDocker管理権限を渡す必要はありません。

実装: [storage.js](../server/storage.js)、[移行スクリプト](../scripts/prepare-media-storage.mjs)。
