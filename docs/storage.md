# 保存先の分離（0.14.0beta以降）

`DATA_DIR`と`MEDIA_DIR`を別々のストレージへ割り当てられます。コンテナ／Node.js直接起動の両方で同じ機能です。ユーザー情報とアセットメタデータは引き続き同じSQLite DBで管理し、DB自体の分割は行いません。

| 保存先 | 内容 | 推奨 |
| --- | --- | --- |
| `DATA_DIR`（コンテナ例 `/data`） | DB・WAL/SHM、アカウント・権限・本棚／シリーズ・アセットメタデータ・閲覧ログ・進行度・ダウンロード鍵・サムネイル／カスタム表紙・プレビュー・管理ジョブ作業領域・管理バックアップ | NASローカルSSDデータセット |
| `MEDIA_DIR`（例 `/media`） | 原本、互換動画／音声、HLS、PDF／EPUB／画像本、分割アップロード・受信／変換途中データ | 大容量HDDデータセット |

閲覧生ログは無期限のためDATA_DIRの容量も増えます。バックアップ作成時にはDATA_DIR側にアーカイブ全体を置ける空き容量が必要です。動画の作業／保持分を含めMEDIA_DIR側の空き容量も監視します。

## 新規導入

1. 2つの空の専用保存先を作成。実行UID/GID 1000へ必要な読み書き・通過権限だけを付与します。SMB/NFS上にDBを置かず、データセットを一般利用者へ共有しません。
2. `DATA_DIR=/data`、`MEDIA_DIR=/media`を設定し、各データセットを対応するパスへマウントします。相対パスは直接起動ではインストール先基準です。両ルートの入れ子・シンボリックリンクによる分離は使いません。
3. MEDIA_DIRのルートは先に作成／マウントしてください。Mireaはそのルートを勝手に作りません。初回の新規分離は、DBがまだなくMEDIA_DIRが空の場合だけ受け付けます。
4. 起動後、アップロード・閲覧・再生成・暗号化DL・停止再開を確認します。

TrueNASは[専用YAML](../deploy/truenas/compose.yaml)の`SSD_POOL`と`MEDIA_POOL`を実際のプール名へ変更します。同一プールの別データセットでも管理上は分けられますが、物理SSD/HDDを分けるならそれぞれのプールを指定します。ホストパスの自動作成は無効にしています。

通常のDockerでは、単一保存先の互換構成は`docker compose -f compose.release.yaml up -d`。**新規の**分離構成は次です。

```sh
docker compose -f compose.release.yaml -f compose.storage.yaml up -d
```

停止にも同じ2つの`-f`を指定します。`down -v`でボリュームを消さないでください。

## 既存環境からの移行（自動実行しません）

既定ではMEDIA_DIRを未設定にし、従来のDATA_DIR内の配置をそのまま使います。**既存環境へ新YAMLの2マウントを貼るだけでは移行できません。**

1. アップロード／ジョブが終わるまで待ち、Mireaを停止。以降、コピー・設定変更・検証が終わるまで旧／新サーバーを起動しないでください。
2. DATA_DIR全体＋設定をバックアップ。既に分離済みなら両ルート全体を同じ停止時点でバックアップします。鍵・証明書・APK署名を保持します。
3. 0.14.0betaの移行ツールを、保存先へアクセスできる保守ユーザーで実行します。新MEDIA_DIRは空の実在するディレクトリでなければなりません。例のパスを実際の保存先へ置換してください。

```sh
node scripts/prepare-media-storage.mjs --data-dir=/existing/mirea-data --media-dir=/new/mirea-media --acknowledge-stopped --acknowledge-full-backup
```

コンテナイメージにも`/app/scripts/prepare-media-storage.mjs`を含みます。NASのポリシーで許可された一時保守コンテナへ両データセットをマウントし、同じUID/GIDで実行する方法も使えます。Webサービスをroot／特権へ変更したり、Dockerソケットを渡したりしません。通常サービスは止めたままです。

4. ツールは`uploads`・`videos`・`originals`だけを新領域へコピーし、SHA-256を照合します。DB・鍵はコピー／変更せず、元のメディアも削除しません。非空の移行先への上書き・リンク／特殊ファイル・処理中のジョブは拒否します。中断してコピーが残った場合は元データを保持したまま移行先を点検し、別の空の移行先でやり直してください。
5. 成功後、元DATA_DIRを維持してMEDIA_DIRを新領域へ設定。両ルートをマウントして新版を起動し、上記の動作確認を実施します。
6. 古いメディアの残りは自動削除しません。検証とバックアップが済んだ後、管理者が別途整理します。設定だけ旧版へ戻すと旧コピーへの書き込みが再開するため、安易に行わないでください。

`storage-layout.json`とMEDIA_DIRの`.mirea-media.json`は、DB側とメディア側の対応を示す識別ファイルです。マウント漏れ・別インスタンスの領域・分離ON/OFFの無断切替を検出すると起動を止めます。削除・編集して保護を回避せず、対応するバックアップと正しいマウントを復元してください。分離済み領域を別プールへ移す場合も、停止中に識別ファイルを含めて媒体全体をコピーします。

## バックアップ・復旧・更新

- 管理画面の「メタデータのみ」はDB・鍵・設定、「すべて」は両ルートのメディア／サムネイル／プレビューも含みます。アーカイブは従来互換の論理的な`data/`へ集約し、ホストの絶対パスやルート識別ファイルは復元用の配置として固定しません。
- 復旧は空の保存先へ行い、バックアップされた設定のホスト固有パスを確認します。まず集約された`data/`をDATA_DIRに戻し、分離したい場合は停止中に移行ツールを実行してからMEDIA_DIRを有効化します。メディアなしのバックアップだけでは本体を復元できません。
- NASの停止中スナップショットは**両方の保存先と設定を同じ時点**で取ります。DBだけ、HDDだけのバックアップでは十分ではありません。
- 分離環境の更新はNAS Apps／ホスト側で行います。従来のWinVAI01用更新ヘルパーは単一DATA_DIRだけを退避するため、分離時は管理画面のサーバー自動更新を無効にします。単一保存先では従来機能を維持します。
- 復帰は旧コード＋対応する更新前データ／設定の組で行います。停止前のスナップショットを戻さずに分離OFFや旧コピーへ戻すと、新しく追加した作品・記録との食い違いを起こします。

異なるファイルシステムへの公開は、出力先側の一時領域へコピー・照合・同期後に同じファイルシステム上で切り替えます。失敗時に元データや既存の公開世代を先に削除しません。参考: [Node.js 24ファイルAPI](https://nodejs.org/docs/latest-v24.x/api/fs.html)、[Docker Compose volumes](https://docs.docker.com/reference/compose-file/services/#volumes)、[SQLite WALのローカル保存条件](https://sqlite.org/wal.html)。
