# Mirea project workflow

- Use the designated isolated development service and synthetic fixtures for reproduction, detailed diagnostics, and verification. Maintain that service when authorized. Deployment coordinates are supplied privately; never publish the owner's hostnames, addresses, certificate-authority names, storage paths, or the identity of environments used by testers.
- Do not use a user-facing deployment as the automated test environment or collect private asset/history logs. Ordinary server logs may be used when authorized and necessary. State exactly which kind of verification was performed without identifying private infrastructure.
- Feature work normally increments the minor version; bug fixes increment the patch version. Target PRs at `develop` and require formally successful CI before merging or publishing. Explicit user instructions to keep work local, defer version changes, or defer publication take precedence. Build logs alone are not CI success.
- Preserve accounts, media, history, progress, download encryption keys, APK signing identity, TLS certificates, and existing network boundaries. Back up the full data directory and configuration before schema migrations or release switching. Do not bypass TLS verification.
- Keep the web service unprivileged. Privileged maintenance must use a reviewed, narrowly scoped helper. Never include user data or private credentials in source, releases, containers, or CI logs.
- If deployment is blocked by missing authority or an unsafe condition, report it explicitly. Do not widen permissions, disable safety checks, or delete user data to force deployment.
- Public documentation and PRs describe the product, generic installation methods, changes, and verification results. Keep person-specific deployment advice in the private conversation. Use synthetic data and documentation-only example values in screenshots and commands. See `docs/development/documentation.md`.
